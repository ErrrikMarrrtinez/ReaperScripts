# EEL внутри Lua-скрипта REAPER

ReaImGui позволяет скомпилировать строку EEL и вызывать её из Lua. Так можно оставить интерфейс, чтение аудио и работу с проектом на Lua, а тяжёлый численный цикл вынести в EEL. Пользователь запускает один Lua-скрипт; отдельный EEL action, Python, сокет или gmem не нужны.

Это не автоматический перевод Lua в EEL: вычислительный участок нужно переписать. И это не фоновый поток: `Function_Execute` выполняется синхронно. Большую задачу всё равно следует делить на короткие блоки.

Нужен установленный ReaImGui. Примеры используют API `0.9.3`, как Vocaligner. Возможность самостоятельного исполнения описана в [Function_Execute](https://cfillion.ca/reaper_imgui_doc.html#Function_Execute); это не только механизм callbacks для InputText.

## Минимальный пример: массив туда и обратно

Сохранить как Lua ReaScript и запустить в REAPER. Пример только считает четыре числа и печатает результат; проект не меняется.

```lua
local r = reaper
if not r.ImGui_GetBuiltinPath then
  r.MB('Install ReaImGui through ReaPack.', 'Lua + EEL', 0)
  return
end
local ImGui = dofile(r.ImGui_GetBuiltinPath() .. '/imgui.lua')('0.9.3')
local ctx = ImGui.CreateContext('Lua + EEL example')

local kernel = [[
  i = 0;
  loop(count,
    output[i] = input[i] * gain;
    i += 1;
  );
]]
local fn = ImGui.CreateFunctionFromEEL(kernel)
ImGui.Attach(ctx, fn)

-- Адреса в памяти EEL, измеряются в числах, а не байтах.
-- Резервируем 1024 числа под вход и 1024 под выход.
ImGui.Function_SetValue(fn, 'input', 0)
ImGui.Function_SetValue(fn, 'output', 1024)

local function multiply(values, gain)
  local n = #values
  assert(n > 0 and n <= 1024, 'Expected 1..1024 numbers')
  local input = r.new_array(values)
  local output = r.new_array(n)
  ImGui.Function_SetValue_Array(fn, 'input', input)
  ImGui.Function_SetValue(fn, 'count', n)
  ImGui.Function_SetValue(fn, 'gain', gain)
  ImGui.Function_Execute(fn)
  ImGui.Function_GetValue_Array(fn, 'output', output)
  return output.table()
end

local result = multiply({1, -2, 0.5, 0}, 0.5)
assert(result[1] == 0.5 and result[2] == -1 and result[3] == 0.25)
r.ShowConsoleMsg(table.concat(result, ', ') .. '\n')
-- 0.5, -1.0, 0.25, 0.0 (формат чисел может отличаться)

-- Та же скомпилированная функция, новые данные и коэффициент.
local again = multiply({2, 4}, 0.25)
assert(again[1] == 0.5 and again[2] == 1)
```

Для четырёх чисел EEL бессмысленен с точки зрения скорости — пример показывает обмен данными. Выигрыш стоит искать в длинных вложенных циклах, где много вычислений на каждую передачу массива.

## Что означают вызовы

| Вызов | Что делает |
| --- | --- |
| `CreateFunctionFromEEL(code)` | Компилирует программу. Создаём один раз, а не на каждом кадре интерфейса. |
| `Attach(ctx, fn)` | Привязывает время жизни функции к контексту. Для долгоживущего инструмента сохраняем также сам контекст. |
| `Function_SetValue(fn, name, value)` | Записывает число в переменную EEL. Для `input`/`output` это адрес начала массива. |
| `Function_SetValue_Array(fn, name, array)` | Копирует `reaper.array` в память EEL по адресу, хранящемуся в переменной `name`. |
| `Function_Execute(fn)` | Выполняет программу с текущими переменными и памятью. |
| `Function_GetValue_Array(fn, name, array)` | Копирует результат из памяти EEL в заранее созданный `reaper.array`. |
| `array.table()` | Превращает native array в обычную Lua-таблицу, если она нужна дальше. |

В EEL `input[i]` означает ячейку памяти по адресу `input + i`. В примере первая ячейка — `input[0]`, в полученной Lua-таблице — `result[1]`. Адрес `0` допустим.

Передача массива — копирование, не общая память. Lua-таблицу напрямую в `Function_SetValue_Array` передавать нельзя. И не стоит передавать каждое число отдельным API-вызовом: так легко потратить на обмен больше времени, чем сэкономить на математике. При частых вызовах можно переиспользовать native buffers, следя за их размером.

Переменные и память функции сохраняются между вызовами. Счётчики, суммы и выходные значения, которые должны начинаться заново, нужно явно сбрасывать. В примере `i = 0` выполняется каждый раз. Хвост после `count` может содержать старые данные: его не читаем.

## Как это устроено в Vocaligner

В 0.8 отдельный `pitch/neural.lua` исполняет компактный SwiftF0. `pitch/model.lua` — экспортированные веса/фильтры, `pitch/features.lua` — native FFT frontend. EEL VM хранит buffers, а Lua ставит короткие свёрточные задания по каналу и группе частот. Перед первым использованием проверяются native transfer и совпадение свёртки с Lua; при ошибке остаётся Lua fallback. Ни ONNX, ни Python во время работы не нужны. Подробности переноса, лицензия, численная точность и границы offline-проверок — в [pitch/RESEARCH.md](pitch/RESEARCH.md).

Рабочий модуль: [eel.lua](eel.lua). Его вызывает [cleanup.lua](cleanup.lua). Интерфейс получает backend из `engine.label`; при отказе причина попадает в Copy report.

Последовательность такая:

1. Lua читает аудио через REAPER audio accessor. В 0.9.5 [cleanup_dsp.lua](cleanup_dsp.lua) считает окно, FFT и признаки cleanup в EEL блоками до `16 / channels` кадров. Сохраняется прежний Lua + `reaper.array.fft` fallback. Align и Pitch используют прежние FFT-пути.
2. Для каждого кадра анализа хранятся мощности 32 полос шириной 500 Hz. При необходимости они упаковываются в кэшированные native arrays.
3. EEL получает до 1024 кадров за вызов и для каждого суммирует мощность полос с частотными весами.
4. Lua применяет порог, находит участки, строит переходы ослабления, ограничивает их выбранным диапазоном и рисует предпросмотр.
5. В версии 0.7.0 Auto запускает захват, анализ и применение при выборе айтема; в ручном режиме это делает Get. Уже известный айтем восстанавливается из кэша текущей сессии REAPER. Запись огибающей идёт через REAPER API. В этой операции EEL не участвует.

### Что изменилось в 0.5.0

Первичный De-ess/Breaths больше не вычисляет MFCC, chroma и производные для DTW: эти данные нужны Align. Native FFT получает и отдаёт числа блоками через `array.copy()` / `array.table()`, вместо тысяч отдельных обращений к userdata на каждый кадр. Пики для первого отображения запрашиваются отдельно через `GetMediaItemTake_Peaks`, без ожидания спектрального анализа.

Ядро в `eel.lua` считает **взвешенную мощность полос**. С 0.9.5 отдельное ядро `cleanup_dsp.lua` также ускоряет первоначальные FFT и признаки. Lua находит кандидатов, делает конечные по времени pre-open/release, объединяет независимые слои De-ess/Breaths и готовит точки. При изменении только глубины/порога ядро мощности не запускается повторно: готовые мощности уже в кэше. Нативная запись точек огибающей может занять время даже при готовом результате вычислений.

В приложенном самостоятельном EEL-примере с `RebuildVolEnvelope` нет кэша спектральных признаков: ExtState хранит параметры по take GUID, а отпускание ручки снова читает звук. Быстрый цикл делает Butterworth high-pass → follower → компрессию. У follower жёстко задан спад 40 ms; это другая модель детектора. Там также временно меняются playrate/длина айтема и используются SWS-функции. Эти побочные действия сюда не перенесены.

Поэтому утверждать, что EEL «вообще не считает» или что вся обработка Vocaligner уже работает на EEL, было бы неверно. Для дальнейшего переноса нужно сравнивать отдельно чтение, DSP, копирование массивов, построение огибающей и её запись. Скорость исходного EEL и новой версии внутри REAPER пока не сравнивалась.

### Проверка 0.9.5

В ReaImGui доступны стандартные математические функции EEL; его Function API не подключает JSFX FFT. Поэтому cleanup использует собственный radix-2 FFT с заранее рассчитанными перестановкой и twiddle-коэффициентами. Окно Hann, усреднение мощностей каналов, 32 полосы и весь контракт признаков совпадают с `dsp.lua`. Проверка при запуске сравнивает ядро с Lua; ошибка компиляции, самопроверки или исполнения возвращает прежний путь.

Стенд с WDL JIT проверяет моно, стерео в противофазе, 8 каналов, тишину, края блоков, дробную эффективную частоту, отмену и смену источника. На шести пользовательских WAV (15 979 кадров) решения деревьев, границы вдохов и кривые ослабления совпали; разница исходных признаков не превышает 3e-14. Это численная проверка анализа, не прослушивание REAPER.

Кэш теперь пакует регулярные массивы как исходные double без сжатия точности. Старые кривые не упаковываются повторно, повторное сохранение после Apply устранено, поиск айтема сначала читает короткий индекс. В стендовом примере на 30 секундах запись аудиопризнаков сократилась примерно со 122 до 20 ms, сохранение 12 вариантов огибающей — с 78 до 7 ms. Нативные записи огибающей и аудиодоступ в эти числа не входят.

Для полосы с центральной частотой `f` вес равен `1 / (1 + (cutoff / f)^4)`. Это спектральное приближение высокочастотного детектора, не обработка PCM фильтром и не split-band de-esser. Звук ослабляется огибающей громкости целиком в найденных местах.

Память текущего kernel:

| Область | Адреса | Размер |
| --- | --- | --- |
| `input` | 0..32767 | 1024 кадра × 32 полосы |
| `output` | 32768..33791 | До 1024 результатов |
| `weights` | 33792..33823 | 32 веса |

Это 33824 числа double, примерно 264 KiB полезных данных внутри VM, без учёта служебных структур. Lua-кэш признаков и native buffers занимают дополнительную память. При изменении числа полос или размера блока надо пересчитать адреса: EEL сам не знает, где заканчивается наш массив.

При запуске модуль сравнивает небольшой EEL-результат с Lua. Ошибка компиляции, передачи или исполнения включает Lua fallback. При неизменном cutoff готовые спектральные измерения переиспользуются; движение Amount не должно запускать заново чтение аудио, FFT или этот kernel.

## Как переносить другой вычислительный участок

Сначала отделить чистую математику от REAPER-вызовов: массив чисел и параметры на входе, массив или несколько чисел на выходе. Сохранить Lua-реализацию для сравнения. Затем перенести внутренний цикл, задать непересекающиеся области памяти и проверить короткий пример с известным ответом.

Полезны проверки нулевого входа, последнего неполного блока, повторного вызова с меньшим размером, крайних параметров и совпадения с Lua с подходящим численным допуском. Для алгоритмов с состоянием, например IIR-фильтра, явно решить, где оно сбрасывается, а где переходит в следующий блок. Не обнулять историю фильтра на каждой границе блока.

Измерять надо весь путь: упаковка, копирование, `Function_Execute`, обратное копирование и дальнейшая обработка. Короткий EEL-цикл ещё не означает быстрый инструмент, если Lua затем каждый кадр заново собирает огромные таблицы или пишет настройки на диск.

В Vocaligner [job.lua](job.lua) дробит задачу и возвращает управление интерфейсу. `job:call(...)` переносит вызов API в основной цикл скрипта; это наш механизм планирования, а не возможность EEL. `Function_Execute` нельзя прервать посередине: длительность ограничиваем размером блока. Самая дорогая неделимая операция всё равно может превысить бюджет шага.

## Ограничения

- Это EEL-вычислитель, не полноценная среда EEL ReaScript или JSFX. Нельзя перенести целиком скрипт с `GetAudioAccessorSamples`, `gfx`, `reaper.*`, `@sample` и ожидать, что всё заработает. Аудио и проект обслуживает Lua.
- Доступны стандартные [математические операции EEL](https://www.reaper.fm/sdk/js/basiccode.php#js_basicfunc) и [строки](https://www.reaper.fm/sdk/js/strings.php#js_string_funcs), а также документированные функции конкретного callback, когда он используется. Lua-объекты и функции автоматически в VM не попадают.
- `Attach` не запускает программу, `defer` не создаёт поток, `Function_Execute` не работает параллельно с интерфейсом.
- Тут нет синхронизации через gmem. Для отдельного JSFX/EEL-процесса понадобился бы другой протокол; текущей схеме он не нужен.
- Это не перенос PyTorch, нейросети или всех возможностей Python. Ускоряется конкретная численная операция собственного алгоритма.

## Что проверено

Исходный EEL kernel исполнен в отдельной VM из [Cockos WDL NSEEL](https://github.com/justinfrankel/WDL/tree/main/WDL/eel2): несколько блоков, неполный хвост, разные cutoff, совпадение конечных кривых с Lua и fallback. Проверка вне REAPER использует portable backend; это не замер производительности ReaImGui JIT.

Пользовательский отчёт REAPER 7.73 / Vocaligner 0.3.0 уже показывает `EEL (ReaImGui, cached bands)` после self-check, 1804 кадра анализа и 51 ms elapsed для последнего предпросмотра, максимум 6.78 ms на шаг. Это конкретный замер всей задачи предпросмотра, не изолированная скорость EEL и не обещание такого времени на любом айтеме. Ошибка записи envelope в том же отчёте возникала позже, на Lua/REAPER-стороне Apply.

Для деталей API: [CreateFunctionFromEEL](https://cfillion.ca/reaper_imgui_doc.html#CreateFunctionFromEEL), [Function_SetValue_Array](https://cfillion.ca/reaper_imgui_doc.html#Function_SetValue_Array), [реализация ReaImGui Function](https://github.com/cfillion/reaimgui/blob/master/src/function.cpp).

### Замер кэша в 0.4.0

На локальном стенде Lua 5.4, без REAPER, для 18 секунд синтетических спектральных признаков медиана семи пересчётов порога/силы, диапазона и областей — около 3.1 ms. Подготовка точек огибающей отдельно — около 3.5 ms. Для 180 секунд — около 35 ms и 36 ms соответственно. Это измерения работы Lua на уже готовых признаках; чтение аудио, FFT, отрисовка и нативная запись точек не входят. EEL в замере движения Amount не вызывается: частотные измерения уже кэшированы.

Упрощение огибающей сначала занимало около 163 ms на 180-секундном примере: один большой RDP-проход многократно просматривал одинаковые промежутки между сибилянтами. Разделение по границам отдельных провалов сократило этот этап до примерно 36 ms, сохранив проверяемый допуск. В Copy report отдельно показаны elapsed предпросмотра, сумма времени его рабочих шагов и длительность нативного применения; последний показатель требует замера внутри REAPER.


## Детектор дыхания 0.7.0: ещё один вычислительный модуль

`breath_engine.lua` компилирует отдельную функцию EEL для модели из 160 деревьев. Обучение сделано заранее, а коэффициенты лежат в `breath_model.lua`. Во время работы нет Python: Lua готовит признаки из общего FFT-кэша, EEL проходит деревья, Lua собирает события и огибающую.

Каждый узел — пять чисел: индекс признака, порог, левый потомок, правый потомок, значение листа. Индексы узлов в таблице Lua начинаются с 1; адрес EEL равен `(node - 1) * 5`. Признак 0 обозначает лист. Сначала один раз передаются модель и корни, затем блоками не более 128 кадров — по 55 признаков на кадр. На выходе одно число на кадр. Глубина цикла ограничена, чтобы повреждённые данные не зациклили VM.

Разметка памяти этой функции: узлы с 0, корни с 65536, вход с 69632, выход с 81920. Перед компиляцией проверяется, что модель и блок признаков помещаются в свои области. Это собственная память функции, независимая от де-эссера и gmem. Настройки усиления не требуют ни повторного прохода деревьев, ни повторного FFT. Примеры Learn breath / Keep sound корректируют закэшированный результат отдельным проходом.

При создании выполняется сверка EEL и Lua. Если компиляция, передача массива или выполнение не удались, используется Lua-вычислитель тех же деревьев, а причина попадает в Copy report. Сам EEL не запускает действия REAPER и не записывает огибающую.

В отдельной проверке на настоящем Cockos WDL EEL VM экспортированная модель, Lua и обученная модель дали совпадающие результаты на 4099 кадрах, максимальное расхождение 1.11e-16. Проверен и контракт FFT/55 признаков. Это проверка численного порта; оценка распознавания, данные обучения и ограничения вынесены в [BREATH_MODEL.md](BREATH_MODEL.md).

Кэш 0.7 сохраняет исходные признаки и данные огибающей в `Cache/Vocaligner` внутри resource path REAPER. Непостоянный ExtState содержит ключ сессии и отдельный индекс каждого проекта: повторное открытие окна использует файлы, перезапуск REAPER теряет индекс. Это соответствует требуемому сроку жизни; обычный `SetProjExtState` записывался бы вместе с проектом. Формат бинарный, ограниченный по размеру, без `load()` и исполнения содержимого. Learn breath / Keep sound по-прежнему используют отдельный сохраняемый project ExtState.
